# ADR 0054 — One code-first stack (relocate `@nanobpm/workflow`, reuse don't reimplement)

Status: Accepted
Date: 2026-08-01
Extends: ADR 0053 (derivation is a shared library), ADR 0052 (decoupled Urban runtime)
Repo: nanobpm/nano-ide (`packages/workflow`, `packages/urban-*`, `packages/create-urban-app`)

## Context

There are **three overlapping ways to build a code-first Urban app**, and they do not compose.
A single feature — "author a durable process in TypeScript, persist typed data, serve a screen" —
is solved three times, in two repositories:

| Concern | **Stack 1 — `@nanobpm/workflow`** (nano-bpm) | **Stack 2 — console codegen** (`nano-generated/*`) | **Stack 3 — `@nanobpm/urban-*`** (nano-ide) |
|---|---|---|---|
| Code → BPMN | `defineFlow` — loops, switch, branch, signals, typed envelopes, ejectable | — | `.flow.json` `CodeFlow` — **linear only**, via `urban gen` |
| Typed data | — | `@nanobpm/domain` (`openDomain`) | `DataLayer` / `TypeRepo` |
| Page UI | — | `@nanobpm/app` (ADR 0042) | `urban-runtime` surfaces |
| Worker host | `Worker` | — | `urban-runtime` workers |
| Engine client | `WorkflowClient` | — | `RestEngineClient` / nano-sdk |
| App descriptor | `nanobpm.project.json` | (console) | `nano.app.json` manifest |
| Deploy / serve | hand-wired `main.ts` | — | `urban run` |

The actually-used code-first app (`jwulf/urban-pr-review-codefirst`) is built on **Stacks 1 + 2**:
`@nanobpm/workflow` for the flow, plus console-generated `@nanobpm/{domain,data,app}` mapped in via
the Deno import map (`@nanobpm/domain → ./nano-generated/domain.ts`). It does **not** use the
`@nanobpm/urban-*` packages at all. Meanwhile `@nanobpm/urban-toolkit` ships its **own**, weaker
code→BPMN deriver (`flowToBpmn`/`deriveModelFromFlow`: a single linear lane, no gateways, no
signals) — a second, redundant `defineFlow`.

Two facts make the fix clear:

1. **`@nanobpm/domain` / `@nanobpm/data` / `@nanobpm/app` are not packages.** They are per-app
   **generated code** (`nano-generated/*.ts`, headers read `AUTO-GENERATED by nanobpmn`), aliased
   under `@nanobpm/*` specifiers by the app's import map. Their templates live in
   `nano-bpm/server/src/console/{domain_types,data_sdk,app_pages}.ts`. Publishing them as packages
   makes no sense — they are derived from each app's own schema. ADR 0053 already committed to
   producing them from the toolkit (`urban gen`) rather than the console.
2. **`@nanobpm/workflow` has no reason to live in nano-bpm.** It has zero runtime dependencies, no
   imports from the server/engine/console, and talks to a running gateway purely over the REST v2
   API. It is a self-contained client SDK with its own release pipeline
   (`release-workflow-npm.yml`), sitting in the engine repo by historical accident.

## Decision

**Collapse to one code-first stack, owned by nano-ide, with the REST v2 API as the repo boundary.**

1. **`@nanobpm/workflow` is *the* code-first flow surface.** `defineFlow` (loops, switch, branch,
   durable signals, typed envelopes, code→BPMN+DI derivation, ejectable to model-first) is the one
   authoring API. The toolkit's linear `flowToBpmn` / `deriveModelFromFlow` (`code->model` deriver)
   is **retired** — superseded, not duplicated.

2. **Reuse, don't reimplement.** `@nanobpm/urban` depends on and re-exports `@nanobpm/workflow`
   rather than growing a second flow DSL. Its worker host wraps `workflow`'s `Worker`; its deploy
   path uses `WorkflowClient`. There is exactly one `defineFlow` in the tree.

3. **Relocate `@nanobpm/workflow` to nano-ide** (`packages/workflow`) — its natural home alongside
   the app-building stack (runtime, toolkit, CLI, scaffolder). The engine repo (nano-bpm) keeps
   only the engine, the gateway, and the console **as a host**; it stops *owning* client SDK code.
   The seam between the two repos is the **REST v2 API**.

4. **Minimal packages — no explosion.** The published surface is **three** packages, not six:

   | Package | Role |
   |---|---|
   | `@nanobpm/workflow` | Flow authoring + derivation + `Worker`/`WorkflowClient`. The one flow engine. |
   | `@nanobpm/urban` | `urban-runtime` + `urban-toolkit` + CLI, merged. Depends on + re-exports `@nanobpm/workflow`. `urban gen` runs the derivers (incl. the domain/data/app codegen moved from the console); `urban run` serves. |
   | `create-urban-app` | Scaffolder. Standalone only because `npm create` requires a `create-*` package. Scaffolds against `@nanobpm/workflow`. |

   `@nanobpm/{domain,data,app,worker,messages,meta}` stay **generated files** in `nano-generated/`,
   aliased by the import map, produced by `urban gen` (ADR 0053) — never packages.

5. **The console consumes the toolkit** (the ADR 0053 migration), rather than owning codegen. The
   toolkit is the single source of the derivers; the console calls it and keeps a drift gate.

## Scope of this change

This ADR lands the **relocation** (plus a small DI-on-deploy feature) — the lowest-risk,
highest-leverage step:

- **nano-ide (this repo):** add `packages/workflow` (a faithful move of nano-bpm's `workflow/`;
  `repository` retargeted to nano-ide, `src`/`test`/`tsconfig` intact). The move also bumps the
  version to `0.5.0`: `deploy` now auto-generates diagram interchange (DI) via `bpmn-auto-layout`
  so derived code-first models are inspectable (graceful degradation when the optional dep is
  absent; opt out with `{ layout: false }`). It joins the `packages/*` workspace and publishes
  through the existing `scripts/publish.mjs` / `release.yml` flow.
- **nano-bpm (separate PR):** delete `workflow/`, `release-workflow-npm.yml`,
  `scripts/workflow-release.mjs`, `docs/releasing-workflow-npm.md`, and CI references, so the
  package is no longer published from two origins.

`0.4.0` is already on npm (published from nano-bpm); this PR bumps to `0.5.0`, so `publish.mjs`
publishes it as the first nano-ide-origin release once the npm **Trusted Publisher** is
reconfigured to point at nano-ide (OIDC; owner-configured).

## Follow-ups (out of scope here, tracked separately)

- Merge `urban-runtime` + `urban-toolkit` into `@nanobpm/urban`; make it depend on and re-export
  `@nanobpm/workflow`.
- Delete the toolkit's linear `flowToBpmn`/`deriveModelFromFlow`; route code→BPMN through
  `@nanobpm/workflow`.
- Move the console codegen templates (`domain_types`/`data_sdk`/`app_pages`) behind `urban gen`;
  console delegates (ADR 0053 migration steps 1–3).
- Re-point `create-urban-app`'s template at `@nanobpm/workflow`.

## Consequences

- One authoring surface, one derivation path, one runtime — the `urban-pr-review-codefirst` app
  becomes a first-class `@nanobpm/urban` app instead of a hand-wired outlier.
- Clean repo boundary: nano-ide owns the app-building SDK; nano-bpm owns the engine. Neither
  reaches across except over REST v2.
- Fewer packages (3, down from 6) and no new domain/data/app packages.
- Risk: publish origin moves mid-life for `@nanobpm/workflow`. Mitigated by keeping the version and
  API byte-identical in the move and by removing the nano-bpm release path in lockstep, so only one
  origin can publish at a time.
